# @zubra/runtime

The browser runtime that compiled Zubra components run on. It is a **polyfill boundary**: everything
compiled code depends on is shaped like a proposed web platform primitive, so when the platform
ships one, this package deletes code instead of components being rewritten.

| Module | Shaped like | Status |
|---|---|---|
| `src/signal.js` | [TC39 Signals](https://github.com/tc39/proposal-signals) (`Signal.State`, `Signal.Computed`, `Signal.subtle`) | Done. Uses native `globalThis.Signal` when present, otherwise `src/signal-impl.js` |
| `src/effect.js` | Not a proposal — the Signals proposal leaves effects to libraries. Built only on `Signal.subtle.Watcher` and microtasks | Done |
| `src/element.js` parts (`walk`/`bind`) | [DOM Parts](https://github.com/WICG/webcomponents/blob/gh-pages/proposals/DOM-Parts.md): a template plus the locations of its dynamic parts | Done: text, attributes, properties, events, `zb-if`/`zb-each` regions (keyed rows move with `moveBefore()`), slots; paths count elements and comments only, and a region counts once |
| `src/element.js` `define` | Custom elements, light DOM by default, shadow opt-in | Done: signal-backed props, typed attributes, pre-upgrade capture, hydration without re-rendering, pause on detach |
| `src/element.js` hooks | Plain functions (see the project's hooks decision) | `state`, `from`, `computed`, `watch`, `onMount`, `onUnmount`, `id`, `props`, `host`, `emit`, `hydrated` |
| `src/element.js` slots | Light-DOM slotting with the host's child methods routed to the slots, so frameworks can keep managing the children; native `<slot>` in shadow DOM | Done |
| `src/react.js`, `src/vue.js` | Adapters: an element as a React (18, 19) or Vue 3 component | Done |
| `src/navigation.js` | Links inside components through the app's router: `routeLinks(navigate)`; `useRouteLinks` in the React and Vue adapters. Not a router | Done |
| `src/forms.js` | A control as a form library's field: React Hook Form (`registerProps`, `fieldProps`), TanStack Form (`fieldProps`), VeeValidate (`vueFieldProps`), Felte (`felteControl`) | Done |
| `src/bridge.js` | Signals read from framework code: `subscribe`, and `toStore` (the Svelte store contract and an RxJS-style Subscribable); React and Vue `useSignal` | Done |
| `types/` | TypeScript declarations for every entry point | Done |
| `src/element.js` forms | Form-associated custom elements (`ElementInternals`) | `formValue`, `validity`, `onFormReset`, `onFormRestore`, `onFormDisabled`; native control API on the element |
| `src/element.js` context | [Context Protocol](https://github.com/webcomponents-cg/community-protocols/blob/main/proposals/context.md) (`context-request` / `context-provider` events) | `createContext`, `provide`, `inject`; interoperates with any protocol implementation |
| `src/context.js` | The same protocol, provided from the app: `<zb-context>` with `context` and `value` properties; `ZubraContext` in the React and Vue adapters | Done |

## The production build

`dist/production/` is the same modules without hot reloading (the code between `// @hot` and
`// @hot-end` in `src/`). Bundlers pick it through the `production` export condition (Vite and
webpack do in production builds), and `@zubra/server` serves it when `NODE_ENV` is `production`.
It's generated by `npm run build:production` and checked in; `npm run test:tools` fails if it's
out of date, and measures both builds against their size budgets (13.5 KB and 13 KB gzipped).

## Signals

`src/signal-impl.js` is an independent implementation of the proposed API. It is held to the
proposal's reference polyfill, [`signal-polyfill`](https://github.com/proposal-signals/signal-polyfill),
by **differential tests**: each scenario runs against both, and the logs must be identical,
including values, recompute counts, the order watchers are notified, the order `watched` and
`unwatched` hooks fire, pending lists and introspection.

- 26 hand-written scenarios: caching, equality cut-off, glitch-free diamonds, dynamic
  dependencies, cached errors, cycles, `equals` semantics, watcher re-arming, frozen-graph rules,
  liveness hooks, introspection, receiver checks.
- 300 seeded random graphs (states, computeds with data-dependent branches and errors, two
  watchers, random reads, writes, watch/unwatch). A one-off run of 5,000 seeds also matched.

### Deliberate differences from the reference polyfill

Each one only affects programs that break a rule the proposal states, so correct programs
behave the same on both. All are tested in `test/signal.test.js`.

1. **Reads and writes inside `watched`/`unwatched` hooks throw.** The proposal says hooks run
   with the graph frozen; the reference doesn't enforce it, and a hook that reads its own signal
   recurses until the stack overflows.
2. **Reading a computed inside a Watcher's `notify` throws before recomputing.** The reference
   starts recomputing first, so the computed caches the "read during notification" error and
   keeps throwing it after the notification is over.
3. **`new Signal.Computed(x)` requires a function** (TypeError), instead of failing on first read.

## Effects

```js
import { Signal } from '@zubra/runtime/signal';
import { effect, scope, flush, tick } from '@zubra/runtime/effect';

const count = new Signal.State(0);
const dispose = effect(() => {
  console.log(count.get());
  return () => { /* cleanup before the next run, and on dispose */ };
});
count.set(1); count.set(2);   // one re-run, in a microtask
await tick();
```

- **Batched**: any number of writes in a task cause one re-run per effect.
- **Owned**: an effect created inside another effect (or a `scope`) is disposed when its owner
  re-runs or is disposed. A child's reads never become its parent's dependencies.
- **Ordered**: parents re-run before children; a child replaced by its parent never runs.
- **Isolated**: an error in a re-run is reported (`reportError`, else `console.error`) and the
  other effects still run. Effects that keep re-triggering each other are stopped after 100
  rounds.
- **Pausable**: `scope.pause()` (an element left the DOM) unwatches everything inside it, so
  long-lived signals hold no reference to it; `scope.resume()` re-runs only the effects whose
  inputs changed while paused. This is wc.js v4's leak fix, now provided by `Signal.Computed`'s
  own version checks.

A write to a signal an effect has already read in the same run does not re-run it (same as a
computed in the reference). Derive the value instead of writing it back.

## Signals in framework code

A signal elements read can be read by the app too, so state is shared rather than copied in by
props and back out by events (`@zubra/runtime/bridge`):

```js
import { state } from '@zubra/runtime';
export const cart = state([]);                       // cart-state.js, imported by elements too

// React                                             // Vue
const items = useSignal(cart, { deep: true });       const items = useSignal(cart, { deep: true }); // a ref
// Svelte: const items = toStore(cart, { deep: true }), then {$items.length}
// Solid: from(toStore(cart))     Angular: toSignal(toStore(cart), { requireSync: true })
```

`subscribe` and the stores are effects owned by nothing: they last until unsubscribed (Vue's ref
stops with the scope it was made in; React's hook with the component). `deep: true` reads through
an array or plain object, so a mutation inside it notifies.

## Tests

```sh
npm install
npm test               # Signals, effects (Node only)
npm run test:browser   # compiled components in Chromium; needs Rust and Playwright
```

The browser tests compile real `.zb` files with the Rust CLI and check fresh rendering, batched updates, pre-upgrade properties, hydration that keeps every server node, anchored text, mismatched markup, a `state()` + `onclick` counter, mount/unmount hooks across a detach and re-attach, and runtime URL blocking; and for regions (`regions.test.js`): lists growing, shrinking and updating rows in place, branches switching (including a list inside a hidden branch), a branch not re-rendering when its test re-runs to the same result, per-row updates that leave other rows' nodes alone, text directly inside rows, and hydration of server-rendered branches, rows and else branches; and for keyed lists (`keyed.test.js`): reordering that keeps each row's element, typed input and focus, middle inserts and removals, in-place updates under the same key, runtime duplicate keys, and hydrated keyed lists; and for slots (`slots.test.js`): light-DOM projection that moves the element's own nodes, live fallbacks, slotted content surviving an `zb-if` toggle, unknown slot names, hydration of supplied content and fallbacks, and native slots in shadow components, fresh and from a declarative shadow root; and for context (`context.test.js`): nearest-provider answers, nested providers, consumers defined before providers, late provider announcements, moving and removing consumers (including unsubscribing), interop with bare-protocol providers and consumers in both directions, `id()`, and the error for hooks called outside setup; and for forms (`forms.test.js`): submitted values under `name`, `form` and `labels`, reset, validation blocking submission with `:invalid`/`:valid`, disabled fieldsets (including starting and being inserted inside one), restore, and the error for form hooks without `form-associated`. They were mutation-checked: each of twenty-seven deliberate runtime breakages (always rewriting text, never hydrating, not pausing on disconnect, skipping the runtime URL check, counting text nodes in paths, re-rendering a branch on every test run, letting the list effect own its rows, not stepping over regions in paths, never hydrating rows, recreating rows instead of updating them, ignoring keys, not using `moveBefore`, losing keys on hydrated rows, leaving moved rows with a stale index, forgetting slotted content after first use, treating supplied server content as fallback, never slotting the element's children, not recognizing `[!` as a region, letting context requests bubble past a provider, ignoring late providers, not asking again after a move, not unsubscribing on disconnect, providers not pushing updates, `id()` ignoring the host id, not being form-associated, never clearing validity, ignoring reset) fails at least one test. One guard (a form control disabled before its setup ran) never runs in Chromium and is kept, documented as untested, for engines that order those callbacks differently.

The effect tests were mutation-checked: removing the parent-first sort, the `untrack` around
child runs, child disposal on re-run, or unwatching on pause each makes at least one test fail.

Later suites cover composition (`composition.test.js`: props passed as values, slotted content from the parent's scope, keyed child components, hydration of nested server markup, other libraries' elements getting properties once defined), events (`events.test.js`: `CustomEvent` shape, cancelable `before…` events, inner same-named events stopped at the host, shadow components' composed events, a parent re-firing a child's event), slots under framework-style DOM calls (`slots.test.js`), and the adapters in real React 19, React 18 and Vue 3 apps (`adapters.test.js`). Each was mutation-checked the same way; mutations that turned out equivalent were removed from the code or documented where they are.
